Nebula 1.0.0 is the first version under this name: AppForge becomes Nebula, and takes its words from its [glossary](https://github.com/Shuko83/Nebula/blob/1.0.0/docs/glossary.md). An application is now either edited or running, its components create their own objects, and it can be assembled from galaxies: projects placed as single components, which stargates connect to the rest.

## What is new

**AppForge is now Nebula:**

- Forge becomes NebulaStudio, `ForgeApplication` becomes `Nebula::Universe`, and `ExampleForgeApp` becomes `ExampleUniverseApp`.
- The package is `find_package(Nebula 1.0 REQUIRED COMPONENTS Core)`, which gives `Nebula::Core` and `nebula_add_plugin()`. The headers are in `Nebula/`, the namespace is `Nebula`, and the macros are `NEBULA_PLUGIN` and `NEBULA_REGISTER_COMPONENT`.
- Plugins are `.nbdl` files, projects are `.nbp` files, and the logging categories are `nebula.components`, `nebula.plugins` and `nebula.settings`.

**Edition and execution:**

- A component has two states: `Editing`, as it is created and once stopped, and `Running`. `start()` goes from one to the other, and `onStart()` may refuse; `stop()` comes back.
- `Universe::start()` remembers the values of the properties a project saves, and `stop()` gives them back: running an application no longer changes its project, and `save()` writes the values of the edition while it runs. While it runs, `instantiate()`, `rename()` and `remove()` refuse.
- NebulaStudio locks the edition zone while the application runs: nothing is dropped, moved, linked, renamed or removed, and the status bar says why. Properties are read-only, and **New**, **Open...** and **Start** are disabled. Selecting still works.

**Components:**

- A component creates its own objects in its constructor. The class of a plugin only gathers its components: `build(<component>&)` is no longer called, and a plugin class that still declares one does not compile, so that what it created is not silently missing.
- A consumed interface can be declared `Mandatory`: the component does not work without it. It is only a hint for whoever assembles the components, and nothing checks it. `Component::unboundMandatoryInterfaces()` names those bound to nothing.
- `WidgetsPlugin`, a new example of these practices: `MainWindowComponent`, `TopBarComponent`, `ActionComponent` and `CounterComponent` assemble the main window of an application through their interfaces.

**Galaxies and stargates:**

- A galaxy is a project file. The **Galaxies** tab of NebulaStudio lists those of a directory and tells which ones can be loaded: those whose plugins are all known, by their id. For the others, it tells what is missing.
- A galaxy is placed in an application as a single component, as many times as needed, each instance with its own components: dragged from the tab to the edition zone, or with `Universe::instantiateGalaxy()`. Its plugins are found by their id and loaded. A galaxy that would contain itself, directly or not, is refused.
- A stargate exposes interfaces and properties of the components of its galaxy: once the galaxy is placed, it provides, consumes and holds them as a component would. **Add stargate** adds one, **Expose...** on the interface of a component adds one already bound to it, and the property editor shows the properties a placed galaxy exposes.
- A placed galaxy opens in NebulaStudio, with a double-click or **Open galaxy**, and is edited as the application is. **Save Galaxy** (Ctrl+Alt+S) writes its file, then reads every instance of it again, keeping their names, their links and the values of their exposed properties. Leaving a changed galaxy asks whether to save it.
- A project has a description: **File** > **Description...**.

**NebulaStudio:**

- A theme of its own, dark or light as the system is, whose texts and borders reach the AA contrast level of the WCAG, with Space Grotesk for its titles.
- A new logo, and an icon for each term of the glossary.
- A component that cannot work, a mandatory interface being bound to nothing, shows a "!" in amber. The list of problems under the property editor tells what to bind it to; double-clicking a line shows the component.
- The edition zone zooms from 25 % to 400 %: + and -, Ctrl+wheel, and the **View** menu. Dragging it with the middle button held moves it.
- A link is selected with a click, and removed with Del or **Remove link** in its context menu.

**Tests:** a Qt Test executable for each class of Core, and for those of NebulaStudio that need no window, run by CTest and by the CI on each pull request. How to run and write them is described in [docs/testing.md](https://github.com/Shuko83/Nebula/blob/1.0.0/docs/testing.md) (in French).

## Upgrading from 0.3.0

- Rename what your project uses: `find_package(Nebula 1.0 REQUIRED COMPONENTS Core)`, `Nebula::Core`, `nebula_add_plugin()`, `#include "Nebula/…"`, the `Nebula` namespace, `NEBULA_PLUGIN`, `NEBULA_REGISTER_COMPONENT`, and `Nebula::Universe` in place of `ForgeApplication`.
- Move what the `build(<component>&)` functions of your plugin class created to the constructor of each component, and leave the plugin class empty.
- Move what `onInitialize()` did to the constructor or to `onStart()`: `initialize()`, `onInitialize()` and the `Ready` state are gone. So are `start(instance)` and **Start component**: nothing is added while the application runs.
- Build your plugins again: a plugin of 0.3.0 is refused, the interface it implements and the major version of Core having changed.
- A project of 0.3.0 is still a JSON file of version 1: give it the `.nbp` extension. The components of the example plugins now have ids starting with `FabienDG.Nebula.` instead of `FabienDG.AppForge.`: replace them in the file. The plugins of other projects keep their ids.

## The package of this release

`Nebula-1.0.0-win64-msvc2022-qt6.8.zip` is built for Windows x64 with MSVC 2022 and Qt 6.8, in `Release` only.

- **To try NebulaStudio:** unzip and run `NebulaStudio/Release/bin/NebulaStudio.exe`. Qt, `ExamplePlugin` and `WidgetsPlugin` are next to it; `ExternalPlugin`, in `ExternalPlugin/Release/lib`, is opened with **Open plugin...**.
- **To build a plugin:** point `CMAKE_PREFIX_PATH` at the unzipped folder, as the README shows in *Building a plugin outside Nebula*. Build it in `Release`, with MSVC 2022 and Qt 6.8: Qt does not load a `Debug` plugin into a `Release` application.
- **For any other setup**, `Debug` included, build Nebula from its sources: CMake 3.19 or later (3.22 for the tests), Qt 6 (Core, Widgets and Svg, and Test for the tests) and a compiler with C++20 concepts and ranges. Clone with `--recurse-submodules`.

## Known limits

- Built and tested on Windows with MSVC only.
- A plugin has to be built again for each version of Nebula: the layout of the classes it derives from may change, and the check made when a plugin is found only compares versions.
- An unloaded plugin keeps its file in use until the application exits: a plugin built again is only read at the next start.
- Nothing is undone in NebulaStudio, and a component is removed without confirmation, with its properties and its links.
- While an application runs, Core refuses to add, rename and remove its instances, but not to bind their interfaces or to change its settings files: only NebulaStudio locks these.
- A mandatory interface bound to nothing is only shown: **Start** does not refuse to run the application.
- An edited galaxy reaches its other instances only once it is saved, and a galaxy file changed outside NebulaStudio is only read again when the project is opened. The problems of the components of a galaxy are not in the list of problems, a settings file of the application cannot hold a property a galaxy exposes, and galaxies are not in the list of components.
- A settings file keeps the values of the user under the names of the instances: renaming an instance leaves them under its former name. Run from NebulaStudio, a settings file without a directory is written to the configuration directory of NebulaStudio, not to that of the application delivered.
- `TopBarComponent` consumes a fixed number of actions and widgets, until a component can consume a list.

## Français

Nebula 1.0.0 est la première version sous ce nom : AppForge devient Nebula, et prend ses mots dans son [glossaire](https://github.com/Shuko83/Nebula/blob/1.0.0/docs/glossary.md#français). Une application est désormais soit en édition, soit en exécution, ses composants créent leurs propres objets, et elle peut s'assembler à partir de galaxies : des projets posés comme un seul composant, que des stargates relient au reste.

## Les nouveautés

**AppForge s'appelle désormais Nebula :**

- Forge devient NebulaStudio, `ForgeApplication` devient `Nebula::Universe`, et `ExampleForgeApp` devient `ExampleUniverseApp`.
- Le paquet est `find_package(Nebula 1.0 REQUIRED COMPONENTS Core)`, qui donne `Nebula::Core` et `nebula_add_plugin()`. Les en-têtes sont dans `Nebula/`, l'espace de noms est `Nebula`, et les macros sont `NEBULA_PLUGIN` et `NEBULA_REGISTER_COMPONENT`.
- Les plugins sont des fichiers `.nbdl`, les projets des fichiers `.nbp`, et les catégories de journalisation sont `nebula.components`, `nebula.plugins` et `nebula.settings`.

**Édition et exécution :**

- Un composant a deux états : `Editing`, tel qu'il est créé et une fois arrêté, et `Running`. `start()` passe de l'un à l'autre, et `onStart()` peut refuser ; `stop()` revient.
- `Universe::start()` mémorise les valeurs des propriétés qu'un projet enregistre, et `stop()` les remet : faire tourner une application ne change plus son projet, et `save()` écrit les valeurs de l'édition pendant qu'elle tourne. Pendant l'exécution, `instantiate()`, `rename()` et `remove()` refusent.
- NebulaStudio verrouille la zone d'édition pendant l'exécution : rien ne se dépose, ne se déplace, ne se lie, ne se renomme ni ne se supprime, et la barre d'état dit pourquoi. Les propriétés sont en lecture seule, et **New**, **Open...** et **Start** sont désactivés. La sélection reste possible.

**Composants :**

- Un composant crée ses propres objets dans son constructeur. La classe d'un plugin ne fait que rassembler ses composants : `build(<composant>&)` n'est plus appelé, et une classe de plugin qui en déclare encore un ne compile pas, pour que ce qu'il créait ne manque pas sans un mot.
- Une interface consommée peut être déclarée `Mandatory` : le composant ne fonctionne pas sans elle. Ce n'est qu'une indication pour qui assemble les composants, et rien ne la vérifie. `Component::unboundMandatoryInterfaces()` nomme celles qui ne sont liées à rien.
- `WidgetsPlugin`, un nouvel exemple de ces pratiques : `MainWindowComponent`, `TopBarComponent`, `ActionComponent` et `CounterComponent` assemblent la fenêtre principale d'une application par leurs interfaces.

**Galaxies et stargates :**

- Une galaxy est un fichier de projet. L'onglet **Galaxies** de NebulaStudio liste celles d'un dossier et dit lesquelles peuvent être chargées : celles dont il connaît tous les plugins, par leur id. Pour les autres, il dit ce qui manque.
- Une galaxy se pose dans une application comme un seul composant, autant de fois que voulu, chaque instance avec ses propres composants : glissée de l'onglet vers la zone d'édition, ou par `Universe::instantiateGalaxy()`. Ses plugins sont trouvés par leur id et chargés. Une galaxy qui se contiendrait, directement ou non, est refusée.
- Une stargate expose des interfaces et des propriétés des composants de sa galaxy : une fois la galaxy posée, celle-ci les fournit, les consomme et les tient comme un composant le ferait. **Add stargate** en ajoute une, **Expose...** sur l'interface d'un composant en ajoute une déjà liée à elle, et l'éditeur de propriétés montre les propriétés qu'expose une galaxy posée.
- Une galaxy posée s'ouvre dans NebulaStudio, par un double-clic ou **Open galaxy**, et s'édite comme l'application. **Save Galaxy** (Ctrl+Alt+S) écrit son fichier, puis relit chacune de ses instances, en gardant leurs noms, leurs liens et les valeurs de leurs propriétés exposées. Quitter une galaxy modifiée demande s'il faut l'enregistrer.
- Un projet a une description : **File** > **Description...**.

**NebulaStudio :**

- Un thème à lui, sombre ou clair selon le système, dont les textes et les bords atteignent le niveau de contraste AA des WCAG, avec Space Grotesk pour ses titres.
- Un nouveau logo, et une icône pour chaque terme du glossaire.
- Un composant qui ne peut pas fonctionner, une interface obligatoire n'étant liée à rien, porte un « ! » ambre. La liste des problèmes, sous l'éditeur de propriétés, dit à quoi la lier ; un double-clic sur une ligne montre le composant.
- La zone d'édition se zoome de 25 % à 400 % : + et -, Ctrl+molette, et le menu **View**. La faire glisser, le bouton du milieu maintenu, la déplace.
- Un lien se sélectionne d'un clic, et se retire par Suppr ou **Remove link** dans son menu contextuel.

**Tests :** un exécutable Qt Test par classe de Core, et par classe de NebulaStudio qui se passe de fenêtre, lancés par CTest et par la CI sur chaque pull request. Les lancer et les écrire est décrit dans [docs/testing.md](https://github.com/Shuko83/Nebula/blob/1.0.0/docs/testing.md).

## Passer de la 0.3.0 à la 1.0.0

- Renommer ce que son projet utilise : `find_package(Nebula 1.0 REQUIRED COMPONENTS Core)`, `Nebula::Core`, `nebula_add_plugin()`, `#include "Nebula/…"`, l'espace de noms `Nebula`, `NEBULA_PLUGIN`, `NEBULA_REGISTER_COMPONENT`, et `Nebula::Universe` à la place de `ForgeApplication`.
- Déplacer ce que créaient les fonctions `build(<composant>&)` de sa classe de plugin dans le constructeur de chaque composant, et laisser la classe du plugin vide.
- Déplacer ce que faisait `onInitialize()` dans le constructeur ou dans `onStart()` : `initialize()`, `onInitialize()` et l'état `Ready` disparaissent. De même que `start(instance)` et **Start component** : rien ne s'ajoute pendant l'exécution.
- Recompiler ses plugins : un plugin de la 0.3.0 est refusé, l'interface qu'il implémente et la version majeure de Core ayant changé.
- Un projet de la 0.3.0 reste un fichier JSON de version 1 : lui donner l'extension `.nbp`. Les composants des plugins d'exemple ont désormais des ids qui commencent par `FabienDG.Nebula.` au lieu de `FabienDG.AppForge.` : les remplacer dans le fichier. Les plugins des autres projets gardent leurs ids.

## Le paquet de cette version

`Nebula-1.0.0-win64-msvc2022-qt6.8.zip` est compilé pour Windows x64 avec MSVC 2022 et Qt 6.8, en `Release` seulement.

- **Pour essayer NebulaStudio :** décompresser et lancer `NebulaStudio/Release/bin/NebulaStudio.exe`. Qt, `ExamplePlugin` et `WidgetsPlugin` sont à côté ; `ExternalPlugin`, dans `ExternalPlugin/Release/lib`, s'ouvre par **Open plugin...**.

## Limites connues

- Compilé et testé sous Windows avec MSVC uniquement.
- Un plugin est à recompiler pour chaque version de Nebula : l'agencement des classes dont il dérive peut changer, et le contrôle fait quand un plugin est trouvé ne compare que des versions.
- Un plugin déchargé garde son fichier ouvert jusqu'à la fermeture de l'application : un plugin recompilé n'est relu qu'au lancement suivant.
- Rien ne s'annule dans NebulaStudio, et un composant est supprimé sans confirmation, avec ses propriétés et ses liens.
- Pendant l'exécution, Core refuse d'ajouter, de renommer et de supprimer des instances, mais pas de lier leurs interfaces ni de changer les fichiers de réglages : seul NebulaStudio verrouille ceux-là.
- Une interface obligatoire liée à rien n'est que montrée : **Start** ne refuse pas de lancer l'application.
- Une galaxy modifiée ne passe à ses autres instances qu'une fois enregistrée, et un fichier de galaxy changé hors de NebulaStudio n'est relu qu'à l'ouverture du projet. Les problèmes des composants d'une galaxy ne sont pas dans la liste des problèmes, un fichier de réglages de l'application ne peut pas tenir une propriété qu'expose une galaxy, et les galaxies ne sont pas dans la liste des composants.
- Un fichier de réglages range les valeurs de l'utilisateur sous le nom des instances : renommer une instance les laisse sous son ancien nom. Lancé depuis NebulaStudio, un fichier de réglages sans dossier est écrit dans le dossier de configuration de NebulaStudio, pas dans celui de l'application livrée.
- `TopBarComponent` consomme un nombre fixe d'actions et de widgets, en attendant qu'un composant puisse consommer une liste.
